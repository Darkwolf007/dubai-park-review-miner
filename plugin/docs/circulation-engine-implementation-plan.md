# Circulation Engine Redesign — Implementation Plan

## Outcome

Replace the current collection of direct program-to-program route curves with one deterministic, connected circulation graph that behaves like a park network:

- a continuous primary pedestrian trunk;
- secondary branches to important destinations;
- tertiary local access paths;
- a physically and logically separate service network;
- access at program boundaries rather than centroids;
- routing that responds to obstacles, permeability, heat/shade, slope, and existing paths;
- stable JSON suitable for Grasshopper/Rhino now and Lands Design later.

The C# core is the authoritative final-design routing engine because it receives the actual Rhino geometry and terrain. The TypeScript application remains authoritative for program, persona, journey, demand, and site-field data. A lightweight web preview may approximate routes later, but it must not become a second independent geometry engine.

## Approved design decisions

1. Program polygons have four circulation behaviors:
   - hard_barrier: buildings, water, fenced play, operations;
   - destination_only: paths may enter only through declared access points;
   - permeable_landscape: paths may cross lawns, plazas, and suitable gardens;
   - preferred_corridor: shaded zones, existing paths, and selected dune valleys.
2. Designers supply exact main, secondary, and service entrances.
3. The engine chooses the principal hub from movement demand, with a designer override.
4. Packed polygons are authoritative. Circles remain fast-preview geometry only.
5. Milestone 1 cost inputs are hard obstacles, program permeability, distance, heat/shade, slope, and existing-path attraction.
6. Milestone 1 delivers primary, secondary, and tertiary public pedestrian paths plus a separate service network.
7. Jogging and cycling loop optimization is deferred to milestone 2.
8. Routes audit the program layout first. They do not silently relocate spaces.
9. Default public hierarchy uses accumulated-flow percentiles: primary top 20%, secondary next 40%, tertiary remainder. Thresholds and widths are Grasshopper inputs.

## Why the current route output fails

The existing RouteGenerator starts from program anchors and emits independent polylines. Even with branch reuse, it does not own a persistent graph, explicit boundary access points, a continuous movement-cost field, or post-route flow accumulation. Consequently:

- visual crossings are not necessarily graph junctions;
- routes terminate at centers or proxies rather than meaningful doors and gates;
- many similar OD links create a starburst or web;
- hierarchy is assigned by route intent rather than measured shared demand;
- polygon permeability is not represented;
- smoothing can invalidate topology;
- route results cannot be reliably audited or edited downstream.

TreemapPathNetworkComponent proves the useful ideas of portals and a connected tree, but shared treemap boundaries are too restrictive to serve as the general circulation engine. Its portal extraction and graph-oriented outputs should inform the redesign, then the component should be retired or converted into a thin adapter.

## Target architecture

### 1. Input and geometry adapters

Add a neutral space-geometry contract in the core:

- SpaceRegion: program ID, polygon ring, circulation behavior, priority, optional access-count override.
- SiteEntrance: ID, point, entrance type, demand weight, accessibility, service permission.
- ExistingPath: polyline, hierarchy/type, attraction weight, retained status.
- CostFieldSource: scalar grid or sampled function with explicit units, bounds, and no-data behavior.

Provide two adapters:

- Polygon adapter: authoritative input from packed Rhino curves.
- Bubble adapter: converts preview circles into polygon rings and marks the result preview_only.

Reject mismatched IDs, open/self-intersecting polygons, out-of-bound geometry, and overlapping hard barriers before routing.

### 2. Separate graph models

Keep three graphs distinct:

- ProgramRelationshipGraph: adjacency, compatibility, avoidance, visibility, and placement rules.
- MovementDemandGraph: OD demand derived from persona journeys, time, mode, entrance demand, and explicit designer overrides.
- CirculationGraph: physical nodes and edges generated by routing.

Movement demand must never be inferred from adjacency strength. The existing canonical movement_demands array becomes the initial OD authority. Extend it later with mode and time buckets without breaking the current schema.

### 3. Access-point generator

Generate candidate access points on polygon boundaries:

1. Add explicit designer doors/gates unchanged.
2. Project nearby entrances and high-demand neighbor directions to each boundary.
3. Add candidates at preferred-corridor intersections.
4. Add evenly spaced fallback candidates for large-perimeter programs.
5. Remove candidates that face hard barriers or violate clearance.
6. Rank candidates by served demand, approach cost, orientation, accessibility, and portal reuse.
7. Select one or more points according to program size/type or explicit override.

Every selected point receives a stable deterministic ID based on program ID, candidate source, and quantized position.

### 4. Movement-cost field

Create one raster/grid abstraction with configurable cell size. Each traversable cell stores normalized channels and a combined cost.

Initial cost:

    cost = distance
         + obstacle_penalty
         + permeability_penalty
         + heat_penalty
         + slope_penalty
         - shade_benefit
         - existing_path_benefit
         - route_reuse_benefit

Rules:

- hard barriers are impassable, not merely expensive;
- destination-only polygons are impassable except for the final approach through a selected access point;
- permeable landscapes receive a configurable crossing cost;
- preferred corridors receive a bounded discount;
- no-data is neutral and reported, never silently treated as ideal;
- all weights are inputs with exported defaults and provenance;
- negative combined costs are forbidden so A* remains valid.

### 5. Demand-led network generation

Build the public network in this order:

1. Resolve site entrances and all selected program access points.
2. Aggregate and normalize OD demand from persona journeys.
3. Choose or accept the primary hub.
4. Route the highest-demand entrance–hub–major-destination pairs first with A*.
5. Burn accepted edges back into the field using a bounded reuse discount.
6. Route remaining OD pairs so they prefer shared trunks before branching.
7. Snap near-coincident segments and crossings into true graph junctions.
8. Split all edges at junctions and remove zero-length/duplicate fragments.
9. Prune low-flow redundant spurs only when every required destination remains connected.
10. Run a final connectivity and obstacle audit.

The service graph runs separately with its own entrances, destinations, widths, obstacle rules, and costs. Public paths may cross service paths only at explicit crossing nodes.

### 6. Flow accumulation and hierarchy

Assign each OD pair to its shortest valid path on the completed graph and accumulate:

- total flow;
- flow by persona;
- flow by time bucket;
- accessible flow;
- entrance-originated flow.

Classify public edges using configurable percentiles, then repair labels topologically:

- primary edges must form a continuous entrance-to-hub trunk;
- secondary edges connect major destinations to that trunk;
- tertiary edges provide local access;
- isolated primary fragments are demoted;
- required accessible paths retain their accessibility classification regardless of flow.

Widths are assigned only after hierarchy. Default widths are UI parameters, not planning-law claims.

### 7. Geometry refinement

Keep graph topology immutable while improving geometry:

- simplify noisy grid steps;
- fit controlled curves within a corridor envelope;
- preserve every junction and access-point coordinate;
- recheck obstacles, slope, minimum radius, and corridor width after smoothing;
- fall back to the unsmoothed valid polyline if refinement fails.

Organic appearance comes from the cost field and controlled refinement, not arbitrary curve noise.

### 8. Diagnostics and outputs

Expose stage toggles and geometry for:

- program permeability;
- access candidates and selected access points;
- individual cost-field channels and combined heatmap;
- raw OD paths;
- reused segments;
- merged graph and junctions;
- accumulated flow;
- hierarchy;
- invalid or unreachable destinations;
- layout-change recommendations.

Add a CirculationAudit result containing disconnected programs, blocked access points, excessive detour ratios, hard-barrier intersections, steep accessible edges, excessive junction density, and low-value spurs.

## JSON contract

Add a versioned circulation block without breaking current consumers:

    circulation_input
      entrances[]
      explicit_access_points[]
      existing_paths[]
      cost_settings
      hierarchy_settings
      service_settings

    circulation_result
      access_points[]
      nodes[]
      edges[]
      od_assignments[]
      analytics
      audit

Each circulation edge should include:

- stable edge ID and endpoint node IDs;
- centerline coordinates;
- length and width;
- public/service network;
- primary/secondary/tertiary/service hierarchy;
- total and categorized flow;
- accessible status;
- environmental cost components;
- source OD and journey IDs;
- reused-route count;
- smoothing status;
- Lands Design target class, layer, material/surface placeholders, and provenance.

The Lands Design handoff should consume circulation_result.edges directly instead of reconstructing semantics from generic route curves.

## Code organization

Create focused core modules rather than expanding RouteGenerator:

- Models/CirculationInputModels.cs
- Models/CirculationGraphModels.cs
- Algorithms/AccessPointGenerator.cs
- Algorithms/MovementCostField.cs
- Algorithms/GridPathfinder.cs
- Algorithms/CirculationNetworkBuilder.cs
- Algorithms/GraphMerger.cs
- Algorithms/FlowAccumulator.cs
- Algorithms/HierarchyClassifier.cs
- Algorithms/PathGeometryRefiner.cs
- Algorithms/CirculationAuditor.cs
- Serialization/CirculationJsonWriter.cs

Add a new Grasshopper component, Generate Circulation, that consumes boundary, authoritative program polygons and IDs, entrances, optional terrain/site fields, package data, and routing settings. It outputs typed public paths, service paths, access points, graph nodes, graph JSON, audit JSON, debug geometry, and summary.

PlanningEngine should call the new engine only when authoritative geometry is available. Its existing bubble RouteGenerator remains a clearly labeled preview fallback during migration.

## Delivery phases

### Phase 0 — Fixtures and baselines

- Save the current failing layout as a deterministic test fixture.
- Define graph, access-point, and cost-field models.
- Add schema examples and golden JSON.
- Record baseline runtime and current route defects.

Exit: fixture loads in tests and produces repeatable IDs and geometry.

### Phase 1 — Valid connected pedestrian graph

- Implement polygon adapter and four permeability classes.
- Implement explicit entrances and boundary access points.
- Implement distance, obstacle, and permeability grid.
- Implement A*, route reuse, graph merging, flow accumulation, and hierarchy.
- Add the Generate Circulation component and debug outputs.
- Keep service routing separate.

Exit:

- every required public destination is connected;
- no public edge crosses a hard barrier;
- all destination-only entries occur at selected access points;
- every visual crossing is either a graph junction or grade-separated metadata;
- hierarchy forms a legible primary trunk with subordinate branches;
- identical inputs and seed produce identical output;
- the reference fixture completes within an agreed interactive runtime.

### Phase 1.1 — Environmental routing

- Add heat/shade, slope, and existing-path channels.
- Add no-data diagnostics and channel normalization.
- Add accessible-route slope audits.
- Export per-edge environmental scores.

Exit: changing one channel predictably changes routes, and disabling it exactly restores the prior result.

### Phase 1.2 — Lands Design handoff

- Export circulation graph JSON.
- Map hierarchy, widths, surfaces, and layers to Lands Design placeholders.
- Update lands_design_handoff.json to reference stable circulation edge IDs.
- Add a bake/update workflow that can replace generated paths without duplicating objects.

Exit: a rerun updates the same Lands Design-target records with stable IDs.

### Phase 2 — Recreational loops

- Add jogging and cycling loop generators as separate optimizers.
- Support target lengths around 250 m, 500 m, and 1000 m as configurable values.
- Score shade, scenic variety, program encounters, terrain, repeated segments, and return-to-start quality.
- Permit controlled reuse of the pedestrian trunk while preserving mode conflicts.

Exit: loops meet target tolerances, close topologically, and pass safety/environment audits.

### Phase 3 — Program-layout feedback

- Convert audit failures into explicit suggested moves or access changes.
- Add optional limited space adjustment followed by rerouting.
- Track objective improvement and stop on convergence/no improvement.
- Never move pinned spaces or designer-approved access points.

Exit: iteration is bounded, deterministic, explainable, and always retains the best valid prior state.

## Testing strategy

Unit tests:

- boundary projection and deterministic access-point IDs;
- permeability transitions;
- A* optimality on known grids;
- reuse-discount bounds;
- segment snapping and junction splitting;
- OD flow conservation;
- hierarchy percentile and continuity repair;
- smoothing validity and fallback.

Invariant tests:

- required destinations are reachable;
- graph edges reference existing nodes;
- no duplicate or zero-length edges;
- no forbidden polygon crossings;
- service and public networks remain distinct;
- accumulated edge flow equals assigned OD flow;
- fixed input and seed produce byte-stable graph JSON after coordinate rounding.

Scenario tests:

- simple entrance–hub–destinations;
- narrow bottleneck;
- disconnected obstacle field;
- multiple access points on a large program;
- competing shaded and short routes;
- steep accessible-route conflict;
- the current Dubai park package and packed-polygon fixture.

Performance tests should report time separately for grid creation, OD routing, merge, flow assignment, hierarchy, refinement, and serialization. This will reveal the true slow stage instead of masking it behind one Grasshopper solve time.

## Migration and cleanup

1. Introduce the new data models alongside current outputs.
2. Add Generate Circulation and validate it against saved fixtures.
3. Switch ParkBubbles polygon workflows to the new engine.
4. Mark RouteGenerator and Treemap Path Network as legacy preview components.
5. Update Lands Design export to consume the circulation graph.
6. Remove legacy routing only after saved Grasshopper files have a documented migration path.

## Explicit non-goals for milestone 1

- automatic program relocation;
- generative-AI geometry;
- full agent-based crowd simulation;
- legal code compliance claims;
- jogging/cycling loop optimization;
- inferred surface materials or construction specifications;
- treating visually crossing curves as connected without an explicit graph node.

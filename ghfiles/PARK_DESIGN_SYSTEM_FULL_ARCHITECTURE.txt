PARK DESIGN SYSTEM - FULL ARCHITECTURE, STRUCTURE, DATA FLOW, AND LOGIC
================================================================================

Document purpose
----------------
This text is the single descriptive reference for the Dubai Park Review Miner,
the ParkDesignPackage export, and the Park Design Space Planner Rhino 8 /
Grasshopper plugin. It explains what each layer owns, how data moves from park
research into geometry, how the deterministic planning algorithms work, how the
Grasshopper components should be wired, and which outputs are authoritative,
schematic, evaluated, or still subject to designer approval.

The system is not intended to replace a landscape architect. It converts a
traceable evidence package into coordinated early-stage spatial proxies. The
designer remains responsible for approving program areas, access points, route
geometry, grading, drainage, planting, materials, safety, accessibility, and
construction details.


1. SYSTEM PURPOSE AND OVERALL ARCHITECTURE
================================================================================

The complete system has five connected layers:

1. Research and evidence layer
   The React/TypeScript application collects park reviews, Google Places data,
   GIS information, demographic indicators, environmental evidence, and design
   opportunities. Local rule-based NLP and optional Gemini analysis classify
   review issues and translate them into traceable design considerations.

2. Synthesis and governance layer
   The Results workspace combines evidence, user groups, program opportunities,
   persona journeys, accepted relationships, site constraints, access candidates,
   terrain intent, planting governance, area reconciliation, and preliminary cost
   assumptions. Evidence does not become a hard geometric constraint merely
   because it was generated by AI. Numeric rules become computational only after
   they are cited and accepted, or explicitly approved by the designer.

3. ParkDesignPackage contract layer
   The browser exports one versioned package. The canonical cross-application
   contract is park_design_package.json, schema v1.4. Compatibility JSON and CSV
   files remain in the ZIP so older definitions and human inspection still work.
   The package is the handoff between web research and Rhino/Grasshopper.

4. Deterministic planning core
   ParkDesign.SpacePlanner.Core is a Rhino-independent .NET 7 library. It loads
   and validates the package, allocates areas, compiles relationships, solves
   bubble positions, places point programs, consolidates shared territories,
   generates paths and morphology guides, evaluates access alternatives, and
   returns inspectable diagnostics. Keeping this logic outside Rhino makes it
   deterministic and testable without opening Grasshopper.

5. Rhino/Grasshopper interaction layer
   ParkDesign.SpacePlanner.gha exposes the core through Grasshopper components.
   It converts Point2 and record models into Rhino curves, points, circles, meshes,
   metadata, corridor edges, and named layers. Terrain components operate on the
   authoritative Rhino mesh. Bake components create controlled Rhino objects only
   when the designer pulses a Button.

End-to-end flow:

Reviews + Places + GIS + climate + personas + accepted rules
        |
        v
React Results synthesis and designer-visible assumptions
        |
        v
ParkDesignPackage v1.4 ZIP / canonical JSON
        |
        v
DesignPackageLoader -> DesignPackageValidator
        |
        v
PlanningEngine
        |
        +--> area allocation and spatial relationship compilation
        +--> area bubbles and relaxation solver
        +--> point nodes and unresolved intent anchors
        +--> shared territories and landscape overlays
        +--> park-path hierarchy, loops, and service access
        +--> dune axes and Baraha alternatives
        |
        v
ParkBubbles Grasshopper outputs
        |
        +--> clean planning geometry -> BakePark -> Rhino layers
        +--> paths -> RouteTerrain -> slope and elevation metrics
        +--> morphology + Barahas + existing mesh -> DuneTerrain
        +--> existing/proposed meshes -> CutFill
        +--> metrics -> designer comparison or Wallacei


2. CONTENTS OF THE ghfiles FOLDER
================================================================================

park.gh
   The main Grasshopper working definition. It should be treated as the primary
   visual orchestration file: package import, program distribution, route outputs,
   terrain processing, evaluation, previews, and bake wiring.

test.gh
   A smaller experimental or verification definition. Use it to isolate component
   behavior before modifying the main definition.

Al Safa Park Plan.3dm
   The Rhino model containing the project geometry and terrain context. Document
   units must remain metres. Horizontal coordinates must match EPSG:32640 inputs.

Al Safa Park Plan.3dm.rhl
   Rhino lock/working-state file. It may exist while Rhino has the 3dm open and
   should not be treated as project geometry or committed as a design deliverable.

al_safa_2_park_design_package_test7/
   Extracted ParkDesignPackage used by the Grasshopper definition. The canonical
   JSON and compatibility files inside provide programs, boundary, grids,
   relationships, movement demand, access, estimates, and morphology data.

net7.0.zip
   Packaged plugin/runtime build artifact. The live Grasshopper installation uses
   ParkDesign.SpacePlanner.gha, ParkDesign.SpacePlanner.Core.dll, and
   ParkDesign.SpacePlanner.deps.json in the Grasshopper Libraries folder.

4. CANONICAL PACKAGE MODEL AND AUTHORITY
================================================================================

The canonical package contains the following logical groups:

Project and coordinate reference
   Project/site identity, package version, timestamps, seed metadata, units, CRS,
   and provenance. Geometry computation requires metres and EPSG:32640. The
   plugin rejects unsupported units or CRS rather than silently transforming data.

Site
   The authoritative site boundary and site-area statements. The measured
   boundary controls geometric containment. A competition brief gross area may
   remain a separate authoritative statement and is not silently substituted for
   measured polygon area.

Grid
   Candidate cells with centroids, optional polygon rings, suitability fields,
   exclusion flags, source authority, and provenance. A designer CAD grid may
   replace the generated grid. Scores transfer from the nearest package cell, but
   geometry authority remains explicitly designer_cad.

Programs
   Area, node, route, system, and overlay programs. Each program can carry stable
   ID, name, ontology, mandatory/selected state, minimum/target/maximum area,
   spatial mode, placement status, location zone, suitability field, user groups,
   temporal and seasonal profiles, performance attributes, dune compatibility,
   route topology, target length, target width, and provenance.

Relationships
   Source and target program IDs, type, weight, mandatory flag, distance limits,
   visibility intent, authority, accepted state, and numeric provenance. Accepted
   rules, designer-approved relations, and advisory edges remain distinguishable.

Journeys and movement demands
   Ordered persona journeys are aggregated into origin-destination demand records.
   Demand weights influence priority and network logic, but do not invent observed
   pedestrian counts. Missing frequency or dwell evidence remains missing.

Access candidates
   Boundary candidates, geographic/project coordinates, role eligibility, hard
   exclusions, raw demand metrics, normalized scores, and pair metrics. Their list
   indices can be Wallacei genes for main, secondary, and service access selection.

Area reconciliation and design estimate
   Separates exclusive land, shared demand, overlay coverage, circulation, path
   lengths and widths, approximate footprints, plant counts, readiness scores,
   and early budget assumptions. These quantities are planning estimates, not a
   bill of quantities.

Climate morphology, terrain, and planting
   Principal site direction, primary sikka, ventilation cuts, Baraha selection
   rules, governed height ranges, terrain authority, coordinate transform, plant
   hydrozones, and automation policy.

Authority rule
   Generated/advisory information may guide ranking and visualization. Only an
   accepted cited rule or explicit designer decision may become a hard requirement.
   Unknown values remain null. The system must not manufacture dimensions merely
   to make geometry appear complete.


5. PACKAGE IMPORT AND VALIDATION LOGIC
================================================================================

DesignPackageLoader accepts four input forms:

1. Preferred ParkDesignPackage ZIP.
2. Extracted package folder.
3. Canonical ParkDesignPackage v1.4 JSON.
4. Legacy compact Results JSON for compatibility.

The loader normalizes these sources into one DesignPackage object while retaining
whether legacy adaptation occurred. It reads role-specific files when necessary,
preserves stable program IDs, separates area/node/route programs, imports grid and
relationship data, retains numeric rule provenance, and loads access, movement,
terrain, morphology, planting, reconciliation, and estimate records.

DesignPackageValidator checks, among other things:

- supported metre units and EPSG:32640;
- valid project and site references;
- boundary and grid compatibility;
- duplicate and missing program IDs;
- target/minimum/maximum area consistency;
- missing program extents and landscape coverage targets;
- relationship source/target references and distance conflicts;
- required numeric provenance;
- journey and OD references;
- unresolved program intent;
- access and package consistency.

Validation messages contain codes and severity. Errors stop unsafe computation.
Warnings keep uncertainty visible without fabricating a solution.


6. PLANNING ENGINE EXECUTION ORDER
================================================================================

PlanningEngine.Generate is the main orchestration method. Its inputs are the site
boundary, loaded package, deterministic integer seed, strategy name, and optional
program behavior. Its stages are ordered because later stages depend on resolved
earlier geometry.

Stage 1 - Strategy selection
   AUTO evaluates Balanced, Suitability, and Connectivity. A named strategy runs
   only that strategy. The same inputs and seed produce the same candidate order,
   geometry, and tie breaking.

Stage 2 - Program area allocation
   ProgramAreaAllocator includes every quantified area program. If exclusive target
   totals fit, exported targets are used. If targets exceed the boundary but the
   documented minimums fit, minimums are used. Shared and overlay demand can overlap
   compatible territories and are not incorrectly counted as exclusive land. The
   engine never scales below documented minimums to force a false fit.

Stage 3 - Relationship compilation
   SpatialRelationshipCompiler creates typed nodes and edges. Accepted rules,
   designer-approved compatibility, and advisory relationships keep separate
   authority. It computes strength components, hard numeric constraints, conflicts,
   statistics, and warnings. Advisory edges may affect preference or diagnostics,
   but cannot silently become mandatory constraints.

Stage 4 - Initial area placement
   BubbleDistributor converts target area A into an area-correct circular proxy
   radius r = sqrt(A / pi). Candidate positions come from eligible grid cells or a
   deterministic fallback. Suitability, boundary clearance, program location zone,
   existing placements, relationship penalties, and seeded tie breaks rank the
   candidates. Exclusive bubbles cannot overlap. Approved shared compatibility can
   reduce separation for shared or overlay behavior.

Stage 5 - Area relaxation
   AreaRelaxationSolver treats spaces as agents and iteratively minimizes a weighted
   energy: suitability loss, overlap, boundary violation, preferred relationships,
   avoid relationships, and accepted hard constraints. It applies bounded movement,
   tracks convergence, and returns program- and edge-level diagnostics. A solution
   with hard violations remains visibly invalid.

Stage 6 - Point and unresolved-area placement
   NodePlacer places node programs and unresolved area-intent anchors after areas.
   It uses eligible grid cells, suitability, adjacency, edge-role requirements, and
   maximin spatial coverage. Maximin coverage prevents generic scores from placing
   every amenity in the same corner. Unresolved areas become explicit intent anchors,
   not invented circles.

Stage 7 - Territory consolidation
   TerritoryConsolidator merges approved compatible shared programs into physical
   shared-territory proxies while retaining all member IDs and nominal demand.
   Landscape overlays are emitted separately as non-additive coverage-equivalent
   proxies, preventing canopy, habitat, planting, and bioswale systems from being
   double-counted as exclusive land.

Stage 8 - Route generation
   RouteGenerator creates the public park-path hierarchy, perimeter exercise loops,
   service spur, and any governed system networks. Detailed logic is in Section 8.

Stage 9 - Climate morphology
   DuneMorphologyGenerator clips the governed primary sikka and ventilation axes to
   the site. Baraha alternatives are ranked around route intersections using the
   exported minimum/maximum radius and route-count rules.

Stage 10 - Scenario score and selection
   Placement completeness, average suitability, and relationship satisfaction form
   an early scenario score. AUTO selects the highest score with deterministic tie
   breaking. Diagnostics remain available for all scenarios; the highest score is
   not automatic design approval.


7. SPATIAL RELATIONSHIP AND SCORING LOGIC
================================================================================

Relationship geometry is not the same as route geometry. Relationship Lines are
thin analytical chords showing preferred, avoid, accepted, or advisory links. They
are useful for debugging the solver, but they should be hidden when reviewing the
designed circulation network. They are deliberately excluded from Clean Geometry.

The main relationship categories are:

- preferred/adjacency: reduce distance or encourage proximity;
- avoid/separation: increase distance or penalize overlap;
- movement/service: indicate relevant network anchors;
- overlap compatibility: allow approved sharing of physical territory;
- mandatory numeric: fail-closed checks using accepted cited dimensions.

Strategy weighting changes emphasis:

- Balanced combines suitability and connectivity;
- Suitability gives more weight to cell/environment scores;
- Connectivity gives more weight to relationships and compact access.

Seed noise only resolves otherwise similar candidates. It is deterministic and
does not authorize a random or unexplained design decision.


8. ACTUAL PARK-PATH GENERATION LOGIC
================================================================================

The path generator is designed as a legible park circulation hierarchy rather than
a minimum-spanning web of unrelated chords.

8.1 Primary walking spine
   The engine searches for mainEntrancePlaza and secondaryEntrances. When both
   exist, they are the public-spine endpoints. If only the main entrance exists,
   the farthest eligible anchor becomes the other endpoint. If entrance metadata
   is unavailable, the deterministic farthest anchor pair defines the spine.

   The spine is routed through a central destination. Preferred central destinations
   are communityPlaza, flexibleEventLawn, and cafeKiosk, in that order when present.
   Otherwise the eligible anchor nearest the site centroid is selected. This makes
   the principal path serve an actual social focus instead of cutting across the
   plan without purpose.

   The spine carries primary, accessible, shade_priority attributes. Its source and
   target IDs remain traceable in Route Proxy Data.

8.2 Secondary walking branches
   Every program not already served by the spine receives one feeder branch. The
   branch starts at the edge of an area bubble rather than its center. Its endpoint
   is the closest point on the primary spine. Persona OD demand determines branch
   processing priority and is written into the route basis metadata.

   This logic produces a trunk-and-branch network: paths converge at controlled
   junctions instead of creating long, visually random program-to-program chords.

8.3 Boundary and obstacle behavior
   Exclusive area bubbles unrelated to a route are obstacles. A visibility graph
   samples clearance points around them, tests line-of-sight segments, and runs a
   deterministic shortest-path search. Every segment is sampled against the site
   boundary. A route should remain inside the boundary and outside unrelated
   exclusive bubble interiors.

8.4 Curvilinear shaping
   A clear two-point connection receives a small deterministic perpendicular bend.
   The direction is derived from a stable string checksum, so the result is repeatable.
   Open routes then receive two Chaikin corner-cutting passes. Each smoothed candidate
   is rechecked against boundary and obstacle rules; unsafe smoothing is rejected and
   the last safe path is retained. The result is a gently curved schematic centerline,
   not a jagged graph edge.

8.5 Jogging and cycling loops
   Jogging and exercise-cycling remain separate closed loops. Each starts from a
   different centroid-inset boundary band so the modes are visually and physically
   distinct. Two closed Chaikin passes round polygon corners. These are conceptual
   perimeter loops; detailed turning radius, crossings, and terrain feasibility must
   still be evaluated.

8.6 Service route
   Service access is a dedicated boundary-to-operations spur. It is not merged into
   public walking paths unless the package later contains an explicit approved rule
   allowing that sharing.

8.7 Route width and corridor geometry
   The package supplies target widths where approved or explicitly assumed. The
   Grasshopper layer offsets each centerline by half the target width using round
   corners, producing left and right Route Corridor Edges. Metadata records program
   ID, side, width, source length, footprint, layer, and allocated early cost.

8.8 What route generation does not yet solve
   Terrain is projected and evaluated after plan routing. The current path generator
   does not yet include slope, drainage, existing trees, utilities, detailed desire
   lines, sight-distance triangles, pavement build-up, true junction fillets, minimum
   cycling radii, or bridge/culvert logic in its pathfinding cost. These are the next
   boundary for construction-level routing.


9. DUNE, BARAHA, AND TERRAIN LOGIC
================================================================================

9.1 Dune morphology axes
   The package supplies a principal direction, primary sikka, and ventilation cuts.
   The plugin clips these planar axes to the site. They are valley/open-air guides,
   not ridge centerlines and not final grading contours.

9.2 Baraha alternatives
   Candidate Barahas are generated near qualifying route intersections. A candidate
   must satisfy the exported minimum distinct route count and governed radius range.
   SelectBaraha greedily keeps ranked, boundary-safe, non-overlapping candidates at
   the designer-set clearance. Rejected alternatives retain audit explanations.

9.3 DuneTerrain displacement field
   DuneTerrain duplicates the authoritative existing mesh; it does not alter the
   source mesh. For each movable mesh vertex inside the boundary:

   - distance to each valley axis is calculated in plan;
   - a smooth cosine bump peaks at the ridge offset on both sides of each axis;
   - wind-erosion/ventilation axes receive a reduced response;
   - explicit Architectural Ridge Zones can use the architectural height;
   - selected Baraha interiors and Protected Territories are pinned near existing
     grade;
   - a protective berm can form outside each selected Baraha;
   - displacement fades to zero at the site boundary;
   - Laplacian smoothing acts on displacement while pinned vertices remain fixed.

   Balance Strength distributes compensating cut over the wider unprotected interior.
   It no longer subtracts the ridge mean only from ridge vertices, which could cancel
   all visible deformation on a coarse mesh. A warning appears when no mesh vertices
   intersect the ridge influence bands; in that case increase Ridge Half Width or
   subdivide/remesh the source terrain.

9.4 Governed/default values
   Landscape Ridge Height defaults to 1.2 m, the midpoint of the exported 0.6-1.8 m
   range. Architectural Ridge Height defaults to 3.25 m, the midpoint of 2.5-4.0 m,
   and has no effect unless explicit Architectural Ridge Zones are connected. Ridge
   Offset, half width, berm width, balance strength, and smoothing passes are visible
   computational decisions requiring designer review.

9.5 Terrain sampling
   TerrainGrid vertically samples a terrain mesh on a horizontal spacing. It returns
   sample points, elevation, slope percentage, and downslope aspect clockwise from
   north. The mesh XY and Z must be in metres and use the same horizontal position
   as the site/package.

9.6 Route terrain evaluation
   RouteTerrain projects centerlines onto the terrain and calculates plan length,
   three-dimensional length, elevation gain/loss, maximum slope, weighted average
   absolute slope, and length exceeding an explicitly supplied maximum slope. No
   hidden accessibility slope is invented. Instantiate separate evaluators for
   walking, jogging, cycling, and service routes.

9.7 Cut and fill
   CutFill samples existing and proposed meshes on a horizontal grid. It estimates
   cut volume, fill volume, signed net, total earthwork, disturbed area, maximum cut
   and fill depths, and balance ratio. It is a vertical-grid planning approximation,
   not a survey quantity. Use coarse spacing during optimization and 0.5-1.0 m for
   shortlisted comparison when mesh resolution supports it.


10. GRASSHOPPER COMPONENT STRUCTURE AND WIRING
================================================================================

10.1 ParkBubbles - Distribute Park Spaces
   Panel: Park Design > Planning.

   Main inputs:
   - closed planar Rhino boundary;
   - package ZIP, extracted folder, canonical JSON, or legacy JSON path;
   - deterministic seed;
   - strategy AUTO/Balanced/Suitability/Connectivity;
   - Run;
   - optional package-boundary selection;
   - optional designer CAD-grid GeoJSON.

   Principal outputs:
   - legacy Bubbles, Centers, Names, Warnings, Summary;
   - Nodes and Node Names;
   - Routes, Route Names, Route Program IDs, and GIS Layers;
   - Loop Routes and Loop Names;
   - Relationship Lines and names, plus separated advisory/avoid/accepted lines;
   - Scenario summaries and solver diagnostics;
   - Resolved Boundary;
   - area intent anchors;
   - Dune Morphology Axes and metadata;
   - Baraha points, candidate footprints, and candidate data;
   - program, user suitability, and relationship JSON metadata;
   - area reconciliation and design estimate JSON;
   - route proxy records and route corridor edges;
   - exclusive, shared, and overlay territory geometry;
   - Clean Geometry, names, and layer paths for controlled baking.

   Recommended preview rule:
   Preview Resolved Boundary, Exclusive Territories, Shared Territories, Landscape
   Overlays, selected public Routes, and chosen Barahas. Hide legacy Bubbles and all
   Relationship Lines when judging design appearance.

10.2 AccessCandidates
   Reads package access candidates and exposes index, point, eligibility, hard
   exclusions, raw metrics, normalized metrics, and metadata. The index is the
   optimization gene, not a stable semantic ID.

10.3 AccessFitness
   Inputs main, secondary, and service candidate indices. It rejects duplicates,
   ineligible roles, school-facing public access, and building-facing/service-invalid
   combinations. Valid results expose raw metrics and eight minimization-ready
   Wallacei values. Maximization objectives are negated. Invalid combinations receive
   1e9 on every fitness output.

10.4 CADGrid
   Reads closed curves/hatches from filtered Rhino layers, validates cells against
   the EPSG:32640 boundary, creates stable north-to-south/west-to-east IDs, reports
   rejected geometry, and writes UTM and WGS84 GeoJSON on an Export button pulse.
   Connect the UTM path to ParkBubbles CAD Grid GeoJSON.

10.5 SelectBaraha
   Connect Resolved Boundary, Baraha Candidate Footprints, and Candidate Data. Set
   maximum count and clearance, then Run. Use Selected Footprints downstream;
   alternatives are not simultaneous built spaces.

10.6 DuneTerrain
   Connect Existing Terrain, Resolved Boundary, Dune Morphology Axes, axis names,
   selected Barahas, and optional protected/architectural zones. Set heights and
   field controls, then Run. Outputs proposed mesh, ridge/valley guides, Baraha
   clearings, per-vertex delta, maximum cut/fill, mean active delta, and summary.

10.7 TerrainGrid
   Connect a terrain mesh, choose sample spacing, and Run. Use the output point,
   elevation, slope, and aspect lists for analysis and visualization.

10.8 RouteTerrain
   Connect one terrain mesh and a filtered route family. Set Mode and sample spacing.
   Enable maximum slope only when an approved value is supplied. Use projected
   Terrain Routes for visualization and numeric outputs for comparison/optimization.

10.9 CutFill
   Connect Existing Terrain and Proposed Terrain. Choose sampling spacing and Run.
   Read volume, disturbance, depth, and balance outputs together; a near-zero net
   value alone does not guarantee acceptable grading.

10.10 BakeRoutes
   Connect Routes, Route Names, and Route GIS Layers. Use a Button on Bake. Replace
   Previous removes only objects previously created by that component instance.

10.11 BakePark
   Connect Clean Geometry, Clean Geometry Names, and Clean Geometry Layers. It bakes
   a curated planning handoff and excludes diagnostic relationship lines. A rising
   Button pulse creates or replaces objects and preserves layer/name organization.


11. RECOMMENDED park.gh CANVAS ORGANIZATION
================================================================================

Organize the Grasshopper definition from left to right in these groups:

GROUP A - Inputs and authority
   Boundary curve, package path, CAD-grid path, existing terrain mesh, seed, strategy,
   run toggles, approved dimensional sliders, and clear text panels documenting CRS,
   units, package version, and terrain source.

GROUP B - Access decision
   AccessCandidates -> candidate preview -> index sliders/genes -> AccessFitness.
   Freeze approved entrance indices before final path review.

GROUP C - Spatial planning
   ParkBubbles with package/boundary/grid inputs. Separate outputs into Areas, Nodes,
   Public Paths, Loops, Service, Relationships, Morphology, Metadata, and Clean Bake.

GROUP D - Clean design preview
   Preview only Resolved Boundary, consolidated territories, overlays, public paths,
   selected Barahas, and morphology guides. Disable relationship and raw-grid preview
   to avoid mistaking analysis graphics for designed objects.

GROUP E - Terrain generation
   SelectBaraha -> DuneTerrain. Connect protected program/path footprints where grade
   must remain controlled. Keep existing and proposed meshes visually distinguishable.

GROUP F - Evaluation
   Separate RouteTerrain components for Walking, Jogging, Cycling, and Service.
   Add CutFill and TerrainGrid. Record approved slope limits beside each evaluator.

GROUP G - Optimization
   Feed raw metrics to Wallacei or another optimizer. Genes may include access indices,
   layout seed, ridge heights, ridge offset, smoothing, balance strength, and later
   route-shaping controls. Objectives should include earthwork, slope violations,
   crossings, repeated edges, useful coverage, and conflicts. Never maximize route
   length alone because it rewards unnecessary loops and wiggles.

GROUP H - Bake and handoff
   BakeRoutes for GIS-specific route layers and BakePark for the curated overall
   planning set. Place Buttons away from Boolean run toggles to prevent accidental bake.


12. RHINO LAYER AND OBJECT LOGIC
================================================================================

The clean bake creates a PARK_DESIGN hierarchy for boundary, movement, territories,
landscape overlays, morphology, and corridor edges. GIS route baking creates a
PARK_DESIGN_GIS movement hierarchy. Objects receive meaningful names and layer paths.
Replace Previous is scoped to objects previously baked by that component instance;
it does not delete arbitrary designer geometry.

Relationship lines, energy diagnostics, rejected candidates, and raw alternative
graphics are analysis-only and should not enter the clean handoff. Baraha alternatives
belong on an Alternatives layer until selected.


13. DETERMINISM, SAFETY, AND TRACEABILITY
================================================================================

- Same package, boundary, seed, strategy, and settings produce the same core result.
- Stable IDs connect geometry to program and evidence records.
- Seed changes explore alternatives but never erase provenance.
- Errors stop unsafe package/coordinate mismatches.
- Warnings expose missing evidence, unresolved areas, coarse meshes, and assumptions.
- Generated geometry remains a proxy until approved.
- AI text cannot become a geometric hard constraint without governed acceptance.
- The existing terrain mesh remains authoritative and unmodified.
- Bake operations require an explicit button pulse.
- No coordinate stretching or silent reprojection is allowed.


14. TESTING, BUILD, AND DEPLOYMENT
================================================================================

From the plugin folder:

dotnet run --project tests/ParkDesign.SpacePlanner.SmokeTests/ParkDesign.SpacePlanner.SmokeTests.csproj
dotnet build ParkDesign.SpacePlanner.sln

The smoke suite validates core logic. A Debug build copies the GHA, core DLL, and
deps JSON into the Grasshopper Libraries directory. Rhino must be closed because it
locks loaded assemblies. If deployment reports MSB3026 or names Rhino as the locking
process, close every Rhino instance, rebuild, reopen Rhino, and recompute the definition.

The project targets .NET 7 for the installed Rhino 8.15 runtime. Package restore may
show NU1701 compatibility warnings because the Rhino/Grasshopper NuGet assemblies
also advertise .NET Framework targets; the current build and smoke tests remain the
practical compatibility checks for this pinned workstation setup.


15. CURRENT LIMITATIONS AND NEXT DEVELOPMENT BOUNDARY
================================================================================

The current system is strong at evidence-to-schematic-masterplan translation, but the
following remain necessary before routes or terrain are construction-ready:

1. Integrate terrain slope directly into pathfinding cost instead of evaluating it
   only after plan routing.
2. Add drainage flow, accumulation, low points, crossings, culverts, and bioswale
   coordination.
3. Add tree preservation, utilities, structures, gates, and designer-drawn no-go
   polygons as route obstacles.
4. Add minimum turning radii, maximum curvature, junction fillets, crossing angles,
   and mode-specific conflict checks.
5. Allow designer-drawn spine/waypoint overrides while retaining generated branches
   and metadata.
6. Provide editable program selection, quantity, area, and strategy approval in the
   Results UI.
7. Persist versioned project snapshots and approved packages in Supabase.
8. Add a Rhino Design Inspector for object-level rule violations and provenance.
9. Add round-trip tests using a representative saved Grasshopper definition.
10. Complete planting intent geometry and neutral planting asset-provider adapters.


16. PRACTICAL DESIGN REVIEW CHECKLIST
================================================================================

Before accepting a generated option, confirm all of the following:

- Boundary, grid, terrain, and package occupy the same EPSG:32640 coordinates.
- Rhino document units and mesh XY/Z units are metres.
- Main, secondary, and service access candidates are valid and explicitly chosen.
- The primary walking spine connects public entrances and serves a meaningful center.
- Feeder paths meet the spine cleanly and do not cross unrelated exclusive programs.
- Relationship Lines are hidden during visual path review.
- Walking, jogging, cycling, and service networks are separated or intentionally shared.
- Corridor widths come from approved settings and fit between program territories.
- Selected Barahas are simultaneous, boundary-safe, and non-overlapping.
- Dune heights remain within approved/governed ranges unless explicitly overridden.
- Protected territories and paths remain at acceptable grade.
- RouteTerrain reports acceptable slope, gain, loss, and violation length.
